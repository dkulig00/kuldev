# 0003: Internationalization — next-intl with [locale] routing

Date: 2026-10-02
Status: accepted

## Context

The site needed PL/EN routes (`/pl`, `/en`) with an `Accept-Language`-based
redirect from `/`. Next.js App Router (16.x) has no built-in i18n routing —
that only exists in the Pages Router — so any approach requires a hand-rolled
`[locale]` segment plus a `proxy.ts`. The candidates were next-intl versus a
hand-rolled minimal solution; both converge on the same `[locale]` +
`proxy.ts` architecture, so the real choice was about `Accept-Language`
negotiation correctness, translation ergonomics, and type safety versus one
new dependency.

## Decision

Adopt next-intl (`^4.14.8`). Its `peerDependencies` explicitly declare support
for `next ^16.0.0` and `react ^19.0.0`, confirmed via the npm registry. Routes
live under `app/[locale]/`, with `src/proxy.ts` performing `Accept-Language`
negotiation and redirecting unprefixed requests. Messages are stored in
`messages/pl.json` and `messages/en.json`, with message keys typed via module
augmentation (`global.d.ts`) so a typo in a translation key fails
`pnpm typecheck`. Locale is read in Server Components via `next/root-params`
`next/root-params` and the locale routes stay fresh on a clean checkout.

Note: the `proxy.ts` `matcher` must be a plain string/array/object literal —
Next.js extracts it via static AST analysis at build time, without executing
the code. A `String.raw` tagged template (or any other non-literal
expression) is silently ignored, causing the middleware to run on every path,
including `_next/static` assets.

## Risk if ignored

A hand-rolled `Accept-Language` parser risks subtle negotiation bugs (q-value
parsing, fallback chains) that are easy to ship silently broken. Building
later on top of next-intl would mean migrating the same `[locale]` structure
anyway, so deferring the dependency wouldn't have saved the architectural work.

## Revisit when

The site's translation needs stay this simple indefinitely and the
dependency's maintenance burden outweighs its negotiation/ergonomics
benefits, or next-intl drops support for a Next.js version the project needs.
